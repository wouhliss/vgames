# Security review, 2026-09-30

Owner: Agent 5 (A5-T13). Every item of [review-checklist.md](review-checklist.md), checked against `main` at
d843f09 (all agents' merged work) plus the open runtime-catalog pipeline (https://github.com/wouhliss/vgames/pull/46).
Each answer names the evidence: a test that fails if the rule breaks (see [test-matrix.md](test-matrix.md)), or the
code read for this review. Findings are filed in `docs/agents/status/agent-5.md` under "Needs from others", addressed
to the owning agent, as for every earlier request.

**Verdict.** No invariant is broken in the code that exists. Six findings, none of them an open exploit: one release
gate (G1) where the code a check applies to does not exist yet, two hardening gaps (F2 before the runtime catalog is
wired, F5), two redaction nits (F3, F4) and one documentation gap (F6). F1, filed with the runbooks, is part of G1.

## Findings

| Id | Owner | Severity | Finding |
|---|---|---|---|
| G1 | Agent 2 | **Release gate** | The launcher's install, update, verify and download commands (`install_start`, `install_update`, `install_verify`, `downloads_*`, …) are called by the UI but not implemented in Rust yet (A2-T08, in progress). The engine they will call is verified and tested (`vgames-transfer::install::fetch_release` → `verify_manifest` before anything is written; chunks checked before they reach their file). Before a release, re-run items 1.1, 1.2 and 2.3 on the wiring: every install and update must go through `fetch_release`/`install`, never write from the release descriptor alone. F1 (Verify adopts the re-signed envelope) belongs here. |
| F1 | Agent 2 | Medium | After a revocation and re-sign, "Verify" must adopt the re-signed envelope of the installed version (02 §9, §11); until then players reinstall. Filed with the runbooks (§3). |
| F2 | Agent 2 | Medium, before the catalog is wired | Keep the highest runtime-catalog version seen **per catalog key**, or a stolen key signing a huge version locks launchers out of every later catalog (runbooks §7). |
| F3 | Agent 1 | Low | `vgames_proto::auth::{TokenRequest, TokenResponse}` derive `Debug` over `code`, `code_verifier`, `access_token` and `refresh_token`. Nothing logs them today; a manual `Debug` that prints `[redacted]` (like the API's `Secret`) keeps one careless `?value` from writing tokens to a log. |
| F4 | Agent 4 | Low | `vgames_overlay::protocol::ToBroker::Hello` derives `Debug` over the per-launch 32-byte broker token. Same fix as F3. |
| F5 | Agent 4 (launcher), Agent 1 (API) | Medium | Realtime: the launcher connects with tungstenite's defaults (64 MiB messages, 16 MiB frames) although the server never sends a frame above `MAX_FRAME` (64 KiB): a compromised server can make each launcher buffer 64 MiB per message. Set `max_message_size`/`max_frame_size` on `connect_async_with_config` to a small multiple of `MAX_FRAME`. Neither side has the no-panic property test 01-security §9 asks for the realtime envelope decoder (arbitrary and mutated frames); both decode through serde, so this is a missing test, not a known crash. |
| F6 | Agent 5 (`contract:` PR) | Documentation | HMAC-SHA-256 (the `hmac` crate) signs fs storage links and page cursors, but 01-security §2 does not list it. It is the standard primitive for both (the fs backend mirrors GCS V4 HMAC signing); add it to the table rather than change the code. |
