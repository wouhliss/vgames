# 01 — Security Architecture

Security invariants (release blockers — every agent must preserve them):

1. **The launcher never executes, or writes into an install, a byte that was not authenticated.**
   Package bytes chain to the server root key pinned by the user (publisher signatures). Compatibility
   runtimes (Proton, umu, Wine, DXMT, …) are pinned by hash in the runtime catalog signed by the vgames
   project key (09-compatibility §5). The launcher and its overlay binaries are covered by the updater
   signature and OS code signing.
2. **A compromised vgames server cannot make launchers run arbitrary code.** Signing
   keys never touch the server; the server only relays signed manifests.
3. **Message plaintext never leaves the endpoints.** The server stores and relays ciphertext only.
4. **The launcher WebView holds no secrets and has no direct network or filesystem access.**
5. **Every privileged server action is authenticated, authorized, rate-limited and audit-logged.**

## 1. Threat model

| Adversary | Can | Must not be able to |
|---|---|---|
| Network attacker | Observe/modify traffic, run a fake server at a typo URL | Read tokens or content (TLS), swap package bytes (signatures), impersonate a pinned server (root pinning) |
| Compromised or malicious **server** | Serve any bytes, see metadata, lie about lists | Get a launcher to run unsigned or tampered code; read messages; read tokens for other servers |
| Malicious **admin UI content** (package description, cover, invite text) | Put arbitrary strings in the UI | Execute script (CSP, no raw HTML), reach tokens (none in WebView) |
| Malicious **website** | Open `vgames://…` links | Launch anything not already installed and verified; add a server or complete a login without user confirmation |
| Malicious **friend** | Send messages/invites | Inject launch arguments (join secrets are validated against a strict grammar), spam (rate limits, blocks) |
| Stolen **admin web session** | Act as that admin until revoked | Publish runnable code (needs the publisher key, which the browser only holds in a Worker while unlocked); change roles (owner only) |
| Stolen **publisher key** | Sign manifests | Stay trusted after the owner publishes a revocation (clients refuse revoked keys) |
| Compromised **CI** | Build a malicious launcher | Ship it without the updater key (humans hold it in protected environments; releases need manual approval) |

Out of scope for v1: anti-cheat (packages have none, and the in-game overlay relies on that), DRM, hiding social metadata from the server, and
compromised end-user machines.

## 2. Cryptographic primitives

| Purpose | Algorithm | Notes |
|---|---|---|
| Content hashing (chunks, files, packs, saves, manifests) | **BLAKE3-256** | Hex lowercase on the wire |
| Signatures (manifests, compat profiles, trust bundles) | **Ed25519** (RFC 8032, `ed25519-dalek` 3, strict verification) | Domain-separated pre-hash, see §3.4 |
| Key files at rest | **Argon2id** (m=64 MiB, t=3, p=1) → **XChaCha20-Poly1305** | Format `vgames.key/1` |
| PKCE | **SHA-256** S256 (RFC 7636) | Interop standard |
| Token / code digests in DB | **SHA-256** | Tokens are 256-bit random, so no KDF needed |
| Randomness | OS CSPRNG (`getrandom`) | Never `rand::thread_rng` for secrets |
| E2EE | **Olm** (3DH + Double Ratchet, Curve25519, AES-256-CBC + HMAC-SHA-256 as specified by Olm) via **vodozemac** | See 05-social §4 |
| Local secret storage | OS keychain (Windows Credential Manager, macOS Keychain, Secret Service) | Fallback in §8 |
| Launcher updates | **minisign** (Ed25519) via `tauri-plugin-updater` + OS code signing | Separate key, see 08-release |
| Runtime catalog (`runtimes.json`) | **minisign** (Ed25519), vgames runtime-catalog key compiled into the launcher; entries pin **SHA-256** of each runtime archive | Separate key from the updater, see 09-compatibility §5 |
| Transport | TLS 1.2+ (rustls), HTTPS mandatory except `localhost` in dev builds | HSTS on the server |

Do not add primitives. Proposing one requires a `contract:` PR to this file.

## 3. Package trust chain

```
  Server ROOT key (Ed25519, offline, owner-held)
        │ signs
        ▼
  Trust bundle vN  ──── lists ───▶ Publisher keys (one per admin/device) + revocations
        │                                   │ signs
        │ pinned by fingerprint             ▼
        │ in each launcher            Package manifest (exact bytes)
        ▼                                   │ lists BLAKE3 of
   Launcher verifies ◀─────────────────── every chunk / file / pack
```

### 3.1 Root key

- Generated by the server owner with `vgames keys init-root` on an offline machine;
  stored as an encrypted `vgames.key/1` file. Keep two copies on separate offline media;
  losing the root means every launcher must re-pin manually.
- Only the **public** key is on the server (`VGAMES_ROOT_PUBLIC_KEY`), published in
  `/.well-known/vgames.json` with its fingerprint.
- **Fingerprint** (shown to users): `VG1-` + first 20 bytes of `BLAKE3(public_key)` in
  Crockford base32, grouped by 4, e.g. `VG1-7K2M-Q9XD-…`. **Key id**: first 16 bytes of
  `BLAKE3(public_key)` as 32 hex chars.
- Launcher pins the root on first connection (TOFU, fingerprint displayed for
  out-of-band comparison) or from a `vgames://server/add?…&fp=` link.

### 3.2 Trust bundle (`vgames.trust/1`)

Exact JSON bytes signed by the root; served by `GET /v1/trust/bundle` as
`{ "bundle": "<base64 bytes>", "signature": "<base64 64 bytes>" }`.

```json
{
  "format": "vgames.trust/1",
  "server_id": "01920000-0000-7000-8000-000000000000",
  "version": 4,
  "issued_at": "2026-09-24T10:00:00Z",
  "expires_at": null,
  "root_key_id": "9f2c…(32 hex)",
  "publishers": [
    {
      "key_id": "a1b2…(32 hex)",
      "public_key": "<base64 32 bytes>",
      "holder_user_id": "0192…",
      "label": "alice@workstation",
      "not_before": "2026-09-24T00:00:00Z",
      "not_after": "2028-09-24T00:00:00Z"
    }
  ],
  "revoked": [
    { "key_id": "c3d4…", "revoked_at": "2026-10-01T12:00:00Z", "reason": "laptop stolen" }
  ],
  "next_root": null
}
```

Rules (implemented once, in `vgames-core::trust`):

- `version` strictly increases. Launchers store the highest version seen per
  server and **reject older bundles** (freeze/rollback protection).
- `expires_at` is optional. If present and past, launchers keep launching
  installed packages but refuse new installs/updates until a fresh bundle arrives.
- **Publisher validity window** (`not_before`/`not_after`) limits when the
  *server accepts new uploads* signed by that key. Launchers do not treat
  expiry as distrust.
- **Revocation** is the only thing that makes launchers distrust a key. All
  manifests signed by a revoked key are invalid until re-signed
  (`vgames trust re-sign` swaps signature envelopes; manifest bytes do not change).
- **Root rotation**: a bundle signed by the old root may set `next_root`
  (`public_key`, `key_id`). Launchers then accept bundles signed by the new root
  and re-pin automatically. There is no other rotation path.
- The server refuses to store a bundle whose signature, `server_id`, or version
  ordering is wrong, and rebuilds `publisher_keys` from the newest bundle.

### 3.3 Publisher keys

- One per admin per signing location: `vgames keys issue-publisher` creates the
  keypair locally; the owner adds the public half to the next trust bundle.
- Private half lives only in an encrypted `vgames.key/1` file on the admin's
  machine. It is decrypted into memory only while packaging:
  - Desktop/CLI: zeroized after signing.
  - Browser: decrypted **inside a dedicated Web Worker** by WASM `vgames-core`;
    the worker exposes only `sign(manifest_hash)`; raw key bytes are never
    posted to the main thread; the worker is terminated after the upload.
- Server check on finalize: signature valid, key in current bundle, not revoked,
  `now ∈ [not_before, not_after]`, and **`holder_user_id == caller`**.

### 3.4 Signature construction

Ed25519 over a domain-separated BLAKE3 pre-hash of the **exact bytes** (never
re-serialized JSON):

```
message = ASCII(context) || 0x00 || BLAKE3(payload_bytes)      // 32-byte digest
context ∈ { "vgames/manifest/v1", "vgames/compat/v1", "vgames/trust/v1" }
```

Manifest signature envelope (`manifest.sig`, JSON):

```json
{ "format": "vgames.sig/1", "alg": "ed25519", "context": "vgames/manifest/v1",
  "key_id": "a1b2…", "payload_blake3": "<hex>", "signature": "<base64 64 bytes>" }
```

Verification order in the launcher (any failure aborts, nothing is written or run):
1. Server root pinned; trust bundle verified under root; bundle `server_id` and version checks pass.
2. `key_id` in bundle and not revoked.
3. `BLAKE3(manifest_bytes) == payload_blake3`, Ed25519 verification passes (strict mode, reject non-canonical S).
4. Manifest parses; `format`, `server_id`, `package_id`, `version_id`, `platform`, `sequence` equal the release descriptor requested.
5. `sequence ≥ installed sequence` (lower = rollback; allowed only through an explicit "install older version" action with a warning).
6. Every path passes `vgames-core::paths` rules (02-package-format §3).

Only then is the manifest used. Chunks are verified against it one by one (02 §7).

## 4. Authentication and sessions

### 4.1 Discord sign-in (desktop)

```
Launcher                              API                                  Discord
  │ verifier=rand32, challenge=S256(verifier), client_state=rand16
  │ POST /v1/auth/discord/start {client:"desktop", code_challenge, client_state, device_name}
  │──────────────────────────────────▶│ store oauth_flow(state_hash, challenge…) TTL 10 min
  │◀── {authorize_url} ───────────────│
  │ open system browser ─────────────────────────────────────────────────────▶│ user consents (scope: identify)
  │                                   │◀── GET /v1/auth/discord/callback?code&state
  │                                   │ consume flow (single use) → exchange code (client secret)
  │                                   │ GET /users/@me → upsert user → registration policy check
  │                                   │ create login_code (32B, TTL 60 s, bound to challenge)
  │◀── 302 vgames://auth/callback?code=<login_code>&client_state=<client_state>
  │ check client_state matches pending flow
  │ POST /v1/auth/token {grant_type:"authorization_code", code, code_verifier}
  │──────────────────────────────────▶│ verify S256(verifier)==challenge, single use
  │◀── {access_token, refresh_token, expires_in, user}
```

- Discord's access token is used once to read the profile and then discarded (never stored).
- If the deep link cannot reach the launcher (for example the scheme is not registered), the callback page
  shows the code with a "copy" button, and the launcher offers a paste field (same PKCE check).
- `registration.mode`: `open` | `allowlist` (default) | `closed`. The Discord id
  in `VGAMES_BOOTSTRAP_OWNER_DISCORD_ID` always passes and becomes `owner` on first sign-in.

### 4.2 Tokens

| Token | Format | TTL | Storage (client) | Storage (server) |
|---|---|---|---|---|
| Access | `vga_` + 43 chars base64url (256 bits) | 15 min | memory + OS keychain | SHA-256 digest |
| Refresh | `vgr_` + 43 chars | 30 days sliding, 1 year absolute | OS keychain | SHA-256 digest (+ previous one for reuse detection) |
| Web session | cookie `__Host-vgames_session` = `vgs_…` | 12 h idle, 7 days absolute | HttpOnly, Secure, SameSite=Lax, Path=/ | SHA-256 digest |
| CSRF (web) | cookie `__Host-vgames_csrf` (JS-readable) mirrored in `X-CSRF-Token` | session | — | SHA-256 digest bound to session |

- Refresh rotates on every use. Presenting a rotated-out refresh token revokes
  the session (`refresh_reuse`) and alerts the user on their other devices.
- Unsafe methods on cookie-authenticated requests require a matching
  `X-CSRF-Token` **and** an `Origin` equal to `VGAMES_PUBLIC_URL`.
- Disabling a user revokes all sessions immediately and closes their sockets.
- Prefixes (`vga_`, `vgr_`, `vgs_`) let secret scanners detect leaks.

### 4.3 Authorization

Roles: `user` < `admin` < `owner`.

| Capability | user | admin | owner |
|---|---|---|---|
| Browse/install published packages, saves, social | ✓ | ✓ | ✓ |
| Create/edit packages, upload/publish/yank versions, metadata | | ✓ | ✓ |
| Disable users (non-admins), manage allowlist, view audit log and jobs | | ✓ | ✓ |
| Change roles, upload trust bundles, change server settings | | | ✓ |

Checks happen in one middleware plus per-handler ownership checks (for example
the caller must be a conversation member). Never trust IDs from the body for
identity; always use the session's `user_id` and `device_id`.

### 4.4 Rate limits (defaults, per server instance)

| Scope | Limit |
|---|---|
| `/v1/auth/*` per IP | 20 / min |
| Authenticated requests per user | 600 / min |
| Friend requests / friend-code redemptions per user | 30 / h |
| Invites per user | 60 / h |
| Message sends per device | 120 / min |
| Signed download URL issuance per user | 2,000 URLs / h |

Exceeding one returns `429` with `Retry-After` and problem code `rate_limited`.

## 5. Server hardening

- **Headers:** HSTS (`max-age=63072000; includeSubDomains`), `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`.
  `/admin/` CSP: `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self';
  connect-src 'self' https://storage.googleapis.com; img-src 'self' data: https://storage.googleapis.com;
  style-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`.
- **Bodies:** JSON limit 1 MiB by default. Manifests are uploaded to storage through a signed URL
  (≤ 256 MiB) and fetched by the server, never posted to the API.
- **Signed URLs:** one object per URL. Downloads: GET, TTL 6 h. Uploads: resumable-session
  start URLs with a TTL of 15 min and a signed `x-goog-content-length-range` header. Never logged.
- **SSRF (metadata images):** HTTPS only; host allowlist (`images.igdb.com`,
  `shared.akamai.steamstatic.com`, `cdn.akamai.steamstatic.com`, `shared.cloudflare.steamstatic.com`,
  `cdn.cloudflare.steamstatic.com`); resolve DNS and reject private, loopback and link-local ranges;
  no cross-host redirects; 10 MiB cap; 15 s timeout; decode with a pixel cap (16384²)
  before storing; re-encode to strip metadata.
- **Text from providers:** HTML converted to plain text/CommonMark subset on ingest; lengths clamped.
- **Database:** the app connects as a least-privilege role (DML only); migrations run as the owner role.
- **Logs:** redact `Authorization`, cookies, `code`, `state`, `token`, and signed URL query strings.
  Never log message ciphertext or key material.
- **Audit:** every admin/owner mutation writes `audit_log` in the **same transaction** as the change.

## 6. End-to-end encryption (summary)

Olm pairwise sessions per device via vodozemac; client-side fan-out to every
recipient device and to the sender's own other devices. The server stores device
identity keys and signed one-time keys, and relays ciphertext envelopes it cannot read.
Details and limits: 05-social §4. Known limits (state them in the UI help):
the server sees who talks to whom and when; new devices do not see old history;
a malicious server could add a device to a user. This is mitigated by device-change
notices and per-contact safety-number verification.

## 7. Launcher hardening

- **WebView:** CSP in `tauri.conf.json` (no remote script, `connect-src` IPC only,
  images from `vgimg:` only), `freezePrototype`, least-privilege capabilities, no
  generic fs/shell/http plugins exposed to JS. Package text is rendered as plain
  text or safe CommonMark (no raw HTML, links open in the system browser only after confirmation).
- **Commands:** every command validates its arguments in Rust (IDs are UUIDs, paths
  must be inside a configured library root after canonicalization, enums closed).
- **Deep links:** strict parser (the grammar is in 00-overview §3.1). Unknown forms are ignored and logged.
  `launch` runs only installed, verified packages with manifest-defined arguments. The URL never
  contributes arguments. Rate limit: 1 launch per 3 s. `server/add` and
  `auth/callback` always need either user confirmation or a matching pending flow.
- **Process launch:** `std::process::Command` with explicit argv (never a shell),
  executable path resolved inside the install dir with no symlink escape,
  environment built from an allowlist plus manifest `env` (validated keys).
- **Join secrets** from invites must match `^[A-Za-z0-9._:\-\[\]]{1,256}$` before
  substitution into manifest-declared `join_args` templates.
- **At rest:** tokens, Olm pickle key and chat-DB key in the OS keychain. If no
  keychain is available (headless Linux), use a `0600` file in the app data dir and
  show a persistent warning in Settings.
- **In-game overlay** (05-social §6): the injected module never opens network connections other than
  the loopback link to the broker, never touches disk, and holds no keys. The broker listens on
  `127.0.0.1` only while a game runs, accepts one connection bearing the per-launch 32-byte token, and
  treats every message from the game process as untrusted input (bounded sizes, closed enums).
- **Compatibility runtimes** are downloaded only from catalog-pinned URLs, verified by SHA-256 before
  extraction, extracted with package path-safety rules, and launched with explicit argv. Compat-profile
  env vars and DLL overrides pass the same validation as manifest env (09-compatibility §4).
- **Single instance** with deep-link forwarding (`tauri-plugin-single-instance`),
  so a second process cannot race the first for installs.

## 8. Supply chain

- Lockfiles committed (`Cargo.lock`, `pnpm-lock.yaml`); CI uses `--locked` / `--frozen-lockfile`.
- `cargo deny` (advisories, licenses: no AGPL/GPL in shipped binaries, banned
  duplicate crypto crates, only crates.io sources), `cargo audit`, `pnpm audit --prod`.
- GitHub Actions pinned by commit SHA; `permissions:` least privilege per job;
  release workflow requires a protected environment with human approval.
- Release artifacts: OS code signing (Authenticode, Apple notarization), updater
  signatures, SHA-256 sums, SBOM (CycloneDX), build provenance attestation.

## 9. Security test requirements

- Known-answer tests: RFC 8032 Ed25519, official BLAKE3 vectors, Google's V4 signing samples.
- Negative tests for every verification step in §3.4 (one test per failure).
- `cargo fuzz` targets: manifest parser, trust bundle parser, signature envelope,
  path validator, deep-link parser, realtime frame decoder, zstd chunk decoder (size-bounded).
- Property tests: pack → download round-trip equals the source tree; path validator
  never accepts a path that escapes the root under any normalization.
- Security review checklist in `docs/agents/agent-5-devops-security.md` runs before every release.
